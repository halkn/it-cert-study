# 認定試験教材の章を執筆する

試験範囲との追跡可能性を保ちながら、初学者が概念、動作、選定基準の順に迷わず学べる章を実装する。
読み物としての演出より、判断に必要な情報へ短い経路で到達できることを優先する。

## 1. リポジトリの基準を読む

作業前に次を読む。

- `CONTRIBUTING.md`
- `shared/policies/content-quality.md`
- `shared/policies/source-policy.md`
- 対象試験の `exam-config.json`
- 対象試験の `docs/coverage-matrix.json` にある対象Objective
- `shared/templates/chapter.md`
- 図や問題を作る場合は対応するtemplate

既存ファイルを正本とし、このSkillとの不一致があれば勝手に緩和しない。

## 2. 試験範囲と根拠を固定する

1. 対象Objectiveと全TopicをCoverage Matrixから抜き出す。
2. 現行の公式Study GuideでObjective名、Topic、試験上の粒度を確認する。
3. 各Topicを支える技術提供元の公式ドキュメントを読む。
4. 技術的主張に使う資料を対象試験の`docs/sources.json`へ登録する。
5. Preview、Edition、region、versionなど変更される条件は検証日と適用範囲を記録する。

非公式記事やLLMの記憶を技術的根拠にしない。
公式資料がObjectiveより詳しい場合は、設問判断に必要な差、条件、代表例に絞る。
Objectiveにない周辺機能を網羅するために章を膨らませない。

## 3. 学習経路を設計する

本文より先に、次を決める。

- 学習後に説明または判断できること
- 前提知識と、前章へ委ねる内容
- 初出用語と表記
- Topicごとの本文位置と根拠
- 図が答える問い
- 章末、Domain、模擬問題で段階的に測る能力

説明は原則として次の順にする。

1. 読者が識別できる具体的な働き、差、または課題
2. その働きに付く公式用語
3. 構造や処理の流れ
4. 条件、例外、混同しやすい境界
5. 要件から機能や設定を選ぶ判断基準

用語名だけを先に置いて暗記させない。

## 4. 初学者向けに書く

`shared/policies/content-quality.md`の「初学者向けの文章設計」に従う。
特に次を守る。

- 一つの段落で一つの論点だけを進める。
- 見出しで対象または問いを特定する。`What`、`How`、`Compare`だけの見出しにしない。
- 結果とともに、結果が生じる機構を説明する。
- 製品、構成、契約区分など異なる選定軸を一括りにしない。
- 具体例、図、SQL、表を試験上の判断へ着地させる。
- 不確実な内容を断定せず、根拠がある内容を曖昧にしない。
- 同じ主張の言い換え、章の進行実況、空疎な強調を削る。

密な説明が続く場合は、図、短い確定事項、比較表、具体例のいずれかで理解を固定する。
本文中に問いを置いた場合は同じ章で答えを回収する。

書籍的な緊張、架空の語り手、思考過程の再演、常に未解決の問いを残す構成は導入しない。

## 5. 教材一式を実装する

章だけで`complete`にしない。
対象Objectiveについて、必要な範囲で次を実装・更新する。

- 章本文と相互リンク
- 公式技術出典とverification log
- 概念理解に必要な図と図registry
- 用語集
- 章末問題
- Domain演習
- 模擬問題
- question registry
- Coverage MatrixとDomain README
- 学習開始ページなどの進捗表示

問題は、章末で概念識別、Domainで比較・組合せ、模擬問題で要件判断を測る。
全選択肢に、正誤の理由と公式根拠を付ける。

## 6. レビューして検証する

次の順に点検する。

1. Topicごとに本文位置、根拠、問題が対応しているか。
2. 初学者が未導入語や未説明の前提で立ち止まらないか。
3. 因果、例外、契約区分、権限、適用条件を過剰に一般化していないか。
4. 章末から模擬問題まで難易度が段階的に上がっているか。
5. 見出しだけを読んで学習経路が分かるか。
6. 章の問い、前方参照、リンクがすべて回収されているか。

最後に次を実行し、失敗を修正する。

```bash
git diff --check
python3 scripts/validate_content.py --exam <対象試験ディレクトリ>
```

検証成功だけを理由に`complete`へ変更しない。
品質基準の全条件を満たしてから状態を更新する。
